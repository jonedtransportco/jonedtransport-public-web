# 02A.15 Contractor Intake Requirements Normalization v1.0

Date: 2026-07-28  
Source reviewed: `Owner op requirements ingles y espanol F.pdf`  
Purpose: convert the current owner-operator intake checklist into a web-ready, role-aware requirements model that can later support `Owner Operators`, `Drivers`, CDL-required profiles, non-CDL profiles, and multiple vehicle types without duplicating flows.

## Scope

This normalization does not activate any public intake, portal automation, real document runtime, or operational onboarding. It only organizes the current requirement set into:

- common intake fields;
- conditional requirements;
- web decision points;
- future reusable intake structure.

## Current source posture

The current document is a valid operational checklist for one specific contractor pattern:

- owner operator;
- truck-based operation;
- driver-attached submission;
- authority and insurance-heavy scenario.

That is useful as source material, but too narrow to be the direct public web model because some requirements are not universal.

## Normalization principle

The public web flow should not present one flat PDF checklist to all applicants.  
It should first classify the applicant, then show only the applicable requirement set.

Recommended decision sequence:

1. applicant profile
2. license type
3. vehicle type
4. authority/commercial status
5. insurance applicability
6. driver-specific operational requirements

## Intake decision model

### Decision 1: applicant profile

The first web decision should identify which path applies:

- `Owner Operator`
- `Independent Contractor`
- `Driver`
- `Other approved contractor profile`

### Decision 2: license requirement

Do not assume CDL as universal.

Allowed paths:

- `CDL required`
- `Non-CDL required`

### Decision 3: vehicle involvement

The web flow should ask whether the applicant is tied to a vehicle and what type:

- `No vehicle at intake`
- `Passenger/light vehicle`
- `Box truck`
- `Straight truck`
- `Tractor`
- `Trailer-attached operation`
- `Other approved vehicle type`

### Decision 4: authority/commercial registration

Only request authority-heavy items when the profile actually needs them:

- DOT
- MC
- carrier authority

### Decision 5: insurance applicability

Insurance requirements must be conditional by profile and vehicle class.

### Decision 6: operational equipment

Items like ELD should remain conditional, not universal.

## Common intake block for the website

These fields should move into a common block used by `Owner Operators`, `Drivers`, and future contractor variants:

- legal name
- business name if applicable
- phone number
- email
- city
- state
- preferred language
- applicant profile
- license type required
- vehicle involvement yes/no

## Conditional blocks for the website

### Block A: business authority

Show only when the profile requires commercial authority:

- DOT
- MC
- carrier authority
- supporting authority document upload

### Block B: license and compliance

Show according to license path:

- license type: `CDL` or `Non-CDL`
- license number
- state of issuance
- expiration date
- license upload
- medical card only if required

### Block C: vehicle

Show only when the applicant is tied to a vehicle:

- vehicle type
- registration
- year
- make
- model
- unit details if later approved

### Block D: insurance

Show only when insurance is required:

- COI upload
- coverage fields
- vehicle-specific coverage variants

### Block E: payout and banking

Show only when that step belongs in intake:

- W-9
- voided check

### Block F: operational equipment

Show only when required:

- ELD
- other equipment-specific confirmations

## Website wording adjustment

The current source is owner-operator-specific.  
The public website should use broader wording first, then narrow by selection.

Recommended top-level wording:

- `Start your application`
- `Tell us what type of contractor or driver profile applies to you`
- `We will show the documents and requirements needed for your profile`

Avoid universal wording like:

- `CDL required`
- `Truck registration required`
- `ELD required`

unless the applicant has already chosen a path where those are truly mandatory.

## Recommended public web structure

### Primary public entry

`jonedtransport.com/owner-operators`

This page should describe:

- who the path is for;
- high-level requirements;
- how the process works;
- start application CTA.

### Intake experience

The intake should be step-based:

1. profile selection
2. license and operation type
3. vehicle and authority
4. document checklist
5. upload and submit

## Separation between public web and portal

### Public website should do

- explain the process;
- capture initial applicant data;
- request applicable documents;
- show conditional checklists by path.

### Portal should do later

- internal review;
- missing-document follow-up;
- status handling;
- internal approval workflow;
- contractor/driver onboarding operations.

## Normalized structure approved for next phase

The current owner-operator checklist should be treated as:

- a valid source checklist;
- one scenario within a broader intake model;
- not the universal checklist for all contractor or driver candidates.

The next implementation baseline should therefore support:

- owner operators with CDL;
- contractor profiles without CDL;
- vehicle-based and non-vehicle-based intake;
- vehicle-type-specific insurance and documentation;
- future driver-specific intake without rewriting the entire structure.

## Immediate next step

Use this document as the baseline to build:

- the public `Owner Operators` page structure;
- the first conditional intake questionnaire;
- the future `Drivers` path using the same normalized framework.
