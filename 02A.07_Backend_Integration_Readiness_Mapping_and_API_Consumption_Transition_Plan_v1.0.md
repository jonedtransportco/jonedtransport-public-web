## Objective

Document the frontend readiness of the JONED Portal Web to move in a future phase from local mock fixtures to approved real APIs, without enabling any live backend connection in this work package.

## Architectural conclusion

The frontend is structurally prepared for future API consumption because the presentation layer, view-model layer and mock adapter layer are already separated. The portal is not operationally ready for real backend enablement because no real API adapter, no server-side authorization enforcement and no contract-parity execution against approved backend services exist in this package.

Current approved flow:

`UI components -> typed view model -> mock adapter -> local fixtures`

Reserved future flow:

`UI components -> typed view model -> API adapter -> approved JONED APIs`

## Readiness classification model

- `READY`: frontend contract shape, decoupled adapter, UX states and low-risk read pattern are already aligned for a controlled future API swap.
- `PARTIALLY_READY`: frontend boundary exists, but the future domain needs additional contract closure, richer state mapping, write-policy decisions or stronger dependency sequencing before API enablement.
- `NOT_READY`: the frontend can display the mock domain, but future real enablement depends on architecture not yet authorized in this work package, especially identity governance, document operations or driver-operation dependencies.

## Cross-cutting findings

### Already prepared across the portal

- Responsive shell, public portal and authenticated workspace are already separated from data-source concerns.
- Role visibility is documented and remains interface-only.
- Shared operational states already exist for `loading`, `empty`, `error`, `partial`, `refresh` and `retry`.
- Normalized list/detail contracts and adapter metadata are already present.
- Module endpoints are already reserved under `/api/v1`.
- Contract switch strategy is already documented as `environment flag + adapter registry + contract parity checks`.

### Still missing across the portal

- No real `api-real` adapter implementation.
- No approved server-side authorization contract.
- No domain-by-domain parity validation against approved backend payloads.
- No canonical error taxonomy from real services.
- No runtime observability or correlation flow for real API failures.
- No approved write semantics for forms or actions that currently remain mock-only.

## Gap register between current mock contracts and expected backend contracts

### Contract gaps

- Mock envelopes define normalized `success` and `error` shapes, but no approved backend canonical field list exists yet by domain.
- Pagination and query-state semantics are prepared in the frontend, but backend cursor/page authority is not yet fixed.
- Filters and sorting options are visible in the UI, but allowed backend values and validation rules remain undefined.
- Partial-response handling is modeled in the frontend, but backend rules for partial completeness are not yet governed.
- Mock role actions expose interface intentions, but no server-side authorization matrix or action-by-action response model is approved.

### Integration gaps

- No API adapter registry implementation is present yet; only the boundary and switch strategy are documented.
- No environment-backed mode switch exists beyond reserved documentation and UI guardrails.
- No per-domain retry policy, timeout policy or stale-data policy is defined for real services.
- No domain contract test suite exists to compare mock and real payload parity before enabling traffic.

### Domain-specific gaps

- `Conductores`: telemetry, availability and acknowledgement behavior need backend authority and sequencing.
- `Administracion`: true permissions, role assignments and governance state must come from an approved identity backend.
- `Documentos`: real document operations must remain separated from operational SharePoint, intake and document-processing runtimes until separately authorized.
- `Configuracion` and `Recursos Humanos`: visible forms need explicit write authorization, validation rules and rollback handling.

Rationale:

- Start with bounded, low-risk, primarily read-heavy domains.
- Move next into domains with stronger statefulness but manageable contract scope.
- Delay domains that depend on governance, document runtime separation or operations-heavy semantics.

## Future transition strategy

### Feature flags

- Use one top-level integration mode flag: `PORTAL_API_MODE=mock|api-real`.
- Add per-domain flags: `PORTAL_DOMAIN_<DOMAIN>_SOURCE=mock|api-real`.
- Keep flags read-only from the frontend bundle; selection should be injected by approved environment configuration.

### Environment switching

- Development and review environments remain `mock` by default.
- Future controlled pre-production validation should allow mixed mode by domain.
- Production activation should occur only after contract parity, UX regression validation and server-side authorization readiness are complete for the specific domain.

### Fallback mock

- Every domain should retain the mock adapter as a reversible fallback during the first real API activation wave.
- Fallback must be domain-scoped; one failing domain must not force the whole portal back to mock mode.
- The UI should continue using existing empty, error, partial, refresh and retry states rather than inventing new behavior during the switch.

### Controlled rollout by domain

- Enable only one domain at a time in `api-real`.
- Execute parity validation before user-visible enablement.
- Require desktop/mobile regression validation after each domain switch.
- Keep operational write actions disabled until the domain proves stable under read-path integration.
