# 02A.15B Contractor Intake Form and Upload Blueprint v1.0

Date: 2026-07-28  
Depends on:

- `02A.15_Contractor_Intake_Requirements_Normalization_v1.0.md`
- `02A.15A_Contractor_Intake_Route_Matrix_v1.0.md`

Purpose: define the future public web intake as a step-based form blueprint with:

- step order;
- visible fields by step;
- upload requirements by route;
- conditional branching behavior;
- implementation-ready field grouping.

## Scope

This blueprint is non-operational.

It does not:

- activate public intake;
- store real applicant data;
- connect document storage;
- perform screening or approval;
- automate onboarding.

It does:

- define the future public form structure;
- organize fields and uploads by route;
- provide a build-ready baseline for design and engineering.

## Primary design objective

The intake should feel simple to the applicant even if the internal requirement logic is complex.

The public experience should therefore:

1. ask only a few routing questions first;
2. hide irrelevant sections;
3. show the checklist that actually applies;
4. avoid forcing legal/operational jargon too early.

## Recommended page structure

The public experience should use one dedicated page:

`jonedtransport.com/owner-operators`

With this flow:

1. overview and CTA
2. short routing questionnaire
3. dynamic intake form
4. dynamic upload checklist
5. review and submit

## Applicant-facing flow

### Screen 1: entry screen

Goal:

- explain that the process adapts to the applicant profile;
- avoid overwhelming the user with every requirement at once.

Visible content:

- short welcome message
- what this process is for
- expected preparation time
- CTA: `Start application`

Recommended copy direction:

- `Answer a few questions and we will show the requirements that apply to your profile.`

## UX guardrails

### Do not do this

- do not show every document to every applicant;
- do not ask for DOT/MC by default on person-without-vehicle routes;
- do not state CDL as universal;
- do not state ELD as universal;
- do not state truck registration as universal.

### Do this instead

- reveal sections progressively;
- show route-aware helper text;
- let `Not sure yet` answers continue the process;
- allow missing upload placeholders for later review instead of hard-stop where appropriate.

## Recommended first implementation scope

For the first public web release, build only:

- `P1`
- `P2`
- `P3`
- `P4`
- `B1`
- `B2`

Keep `B3` and `B4` supported in the logic model, but do not expose them publicly until JONED confirms they are real intake use cases.
