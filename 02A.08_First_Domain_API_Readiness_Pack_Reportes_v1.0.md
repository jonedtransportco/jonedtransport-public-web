## Objective

Prepare the first low-risk portal domain for a future controlled switch from mock mode to real API consumption without enabling any live backend, operational integration, or production activation in this work package.

## Selected domain

Selected domain: `Reportes`

Selection rationale:

- `02A.07` classified `Reportes` as `PARTIALLY_READY`, ahead of `Documentos` and aligned with a future controlled switch.
- The domain is explicitly read-oriented in the current UX and does not require real write-path enablement to prove the first controlled switch.
- The mock module already separates catalog, widgets and scheduling states behind a decoupled adapter boundary.
- The domain avoids document-runtime coupling, operational acknowledgements and identity-governance decisions that still block `Documentos` and `Administracion`.
- The delegated authorization explicitly recommended `Reportes de solo lectura` as an acceptable first domain.

## Required frontend adapter

The first real switch requires a dedicated reports adapter with these responsibilities:

- read the domain flag and choose `mock` or `api-real`
- serialize query state into a real read-only request
- receive the real reporting payload
- normalize service fields into the existing `DomainWorkspaceContract`
- convert service timestamps and enumerations into current display tokens
- map completeness, freshness and retryability into existing UX states
- keep mock fallback available per domain

### Adapter invariants

- UI components do not know whether data came from fixtures or the future Reporting API.
- The reports adapter must not expose raw backend field names directly to presentational components.
- The adapter must fail closed to `mock` or to a controlled error state when parity is incomplete.
- The adapter must not activate any write, export, scheduling or cross-system behavior in the first switch.

## Expected errors and states

### Allowed UX states for first real switch

- `ready`: full catalog and widget summary available
- `partial`: catalog available, some widgets or slices delayed, withheld or incomplete
- `empty`: no reports match current filter scope
- `error`: request failed or contract parity broke
- `loading`: fetch in progress

### Expected error classes

| Error class | Expected UI state | Adapter handling |
| --- | --- | --- |
| upstream timeout | `error` or `partial` depending on cached catalog availability | preserve filters, show retryable message, no hidden fallback to real write actions |
| partial analytical dataset | `partial` | populate catalog and expose missing widgets through `PartialResponseContract` |
| unauthorized read | `error` | show controlled error and keep domain flag revertible to `mock` |
| unsupported filter value | `error` | normalize or reject query before render; avoid undefined UI states |
| contract mismatch | `error` | stop real rendering path, emit correlation id if available, allow domain rollback to `mock` |

## Feature flag and future activation control

Reserved activation model for `Reportes`:

- top-level: `PORTAL_API_MODE=mock|api-real`
- domain-level: `PORTAL_DOMAIN_REPORTES_SOURCE=mock|api-real`

Activation rules:

- review and development remain `mock` by default
- first controlled future validation may use mixed mode with `Reportes=api-real`
- all other domains remain `mock`
- rollback must be domain-scoped
- frontend bundle must not allow user-driven flag mutation

## Acceptance criteria for the first future switch

- domain explicitly remains `Reportes` only
- real adapter returns the same normalized envelope shape already used by the mock frontend
- list, detail, filters, tabs and metrics render without UI redesign
- desktop and mobile regressions pass using the existing UX states
- partial widget coverage is represented only through the approved `partial` state and `PartialResponseContract`
- no export, scheduling, financial logic, document runtime or business automation becomes active
- one-domain rollback to `mock` is available without redeploying the full portal architecture
- server-side authorization for read access exists before any non-mock traffic is allowed

## Gaps and risks

### Gaps

- No approved backend canonical report schema exists yet.
- Export behavior remains visually modeled but operationally undefined.
- Scheduling is present in tabs but not authorized for activation.
- Filter vocabularies and status enumerations are still mock-defined.
- Partial widget semantics are represented in UX but not yet governed by backend policy.

### Risks

- A real reporting service may return richer but structurally different analytical payloads that bypass the normalized adapter if not constrained.
- The current `updatedAt` strings are presentation-ready mock text, while a real service should return machine timestamps and freshness metadata.
- `Reportes` may be pressured to absorb financial reporting sources; this package explicitly prohibits mixing real financial runtime into the first switch.
- Export controls may be misread as authorized because the mock UI already shows an export affordance; first-switch behavior must remain read-only.

## Ordered future integration conditions

1. Freeze the report catalog read-only contract and its filter vocabulary.
2. Define backend error taxonomy, correlation metadata and partial-data rules.
3. Implement the reports API adapter behind the existing view-model boundary.
4. Execute parity tests against the normalized 02A contract.
5. Re-run desktop and mobile UX regression tests with `Reportes` only in `api-real`.
6. Keep export and scheduling disabled.
7. Activate only the `Reportes` domain in a controlled review environment.
8. Maintain immediate domain fallback to `mock`.
