# 02A.24 Public Web Hosting Separation Plan v1.0

Version: 1.0  
Lifecycle: Under_Review  
Authorization state: AUTHORIZED FOR PUBLIC WEB HOSTING SEPARATION PLANNING ONLY

## Objective

Define the correct hosting split for the JONED web presence so that:

- `jonedtransport.com` becomes the public company website
- `portal.jonedtransport.com` remains the controlled internal portal

This package does not activate production hosting by itself. It records the validated blocker, the recommended separation path, and the next controlled implementation sequence.

## Traceability inside `02A`

- preserves the public/private split regularized in `02A.16`
- preserves the public homepage closed in `02A.20`
- preserves the public recruiting routes closed in `02A.17`, `02A.18`, `02A.19`, `02A.22`, and `02A.23`
- preserves the internal portal boundary established across `02A.02` through `02A.14`

## 1. Current validated state

As of `2026-07-28`:

- `jonedtransport.com` resolves publicly
- `portal.jonedtransport.com` resolves publicly
- `www.jonedtransport.com` resolves to `jonedtransport.com`
- both `jonedtransport.com` and `portal.jonedtransport.com` currently inherit restricted access behavior

Validated root cause:

- both hostnames were attached to the same hosted site
- that hosted site uses restricted access
- the public root domain therefore inherited the same access gate as the internal portal

## 2. Confirmed blocker in the current hosting workspace

The current hosting workspace was validated as unsuitable for the final public website because:

- the current site access model is restricted
- the current workspace returned a publish-disabled blocker for public internet exposure

Observed blocker:

- public internet publishing is not enabled for the current workspace

This means the public website should not continue depending on the same hosting target used for the private portal.

## 3. Recommended final split

### Public website

Hostname:

- `jonedtransport.com`

Purpose:

- company presentation
- services
- recruiting
- contact
- public `Owner Operators` and `Drivers` entry routes

Recommended hosting model:

- independent public hosting target
- separate from the private portal runtime
- public access enabled by design

Recommended technical direction:

- keep the current public web experience as its own deployable surface
- publish it on a public-capable hosting target
- do not reuse the portal-restricted access configuration

### Private portal

Hostname:

- `portal.jonedtransport.com`

Purpose:

- controlled role-based operational workspace
- internal review flows
- protected modules and future internal integrations

Required hosting model:

- restricted access only
- separate from the public root-domain site

## 4. Recommended option

Recommended option: `Option B`

Meaning:

- keep `portal.jonedtransport.com` on private/restricted hosting
- publish `jonedtransport.com` on a separate public-capable hosting target

Why this is recommended:

- preserves the approved architecture split
- removes the risk of the public site inheriting private access controls again
- allows the public site to evolve independently for recruiting, intake, and company presentation
- avoids dependence on a workspace-level public publishing blocker that is outside normal frontend control

## 5. Controlled implementation sequence

1. keep `portal.jonedtransport.com` attached only to the private portal site
2. prepare the public website as a separate deployable site
3. publish the public website to a public-capable hosting target
4. attach `jonedtransport.com` only to the public website
5. keep `www.jonedtransport.com` redirecting or aliasing to `jonedtransport.com`
6. verify that the root domain no longer presents restricted-access behavior
7. verify that `portal.jonedtransport.com` remains restricted

## 6. Acceptance criteria

The hosting separation is considered complete only when all of the following are true:

1. `jonedtransport.com` opens without private access gating
2. `portal.jonedtransport.com` remains protected
3. the public homepage renders correctly on the root domain
4. `/owner-operators` renders on the public site
5. `/drivers` renders on the public site
6. the portal remains isolated from the public root-domain experience
7. no production business integration is activated as part of the hosting change

## 7. Risks to avoid

- attaching both hostnames to one restricted site again
- relaxing portal protection in order to open the public website
- introducing backend integration as part of a hosting-only change
- mixing recruiting/public flows with internal portal runtime
